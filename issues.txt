

## What's Actually Working Well

**The core pipeline is genuinely impressive.** The output shows 3 specialist agents (EmailCopywriter, SalesStrategist, CicdExpert) each producing real domain-specific content, then the Orchestrator synthesizing them into a comprehensive executive report. That loop — analyze → plan roster → spawn dynamic agents via LLM-generated code → execute → report — is working correctly end to end.

The `spawn_dynamic_agent` idea is legitimately clever: a CodingAgent writes a new Python class from scratch, the factory loads it dynamically, and it runs. That's real runtime code generation.

## Issues — Status Tracker

### ✅ DONE

**#1 — `exec_module()` on LLM-generated code (security)**
- `validate_generated_agent_code()` added to `core/validator.py` — performs AST syntax check, security scan via `_DANGEROUS_PATTERNS`, structural checks (class name, BaseAgent inheritance, `execute_task` method).
- `coding_agent.py` now validates BEFORE writing to disk — bad code never hits the filesystem.
- `agent_factory.py` has a 3-attempt retry loop that injects validation errors back into the LLM prompt on each retry. Cleans up any bad file on failure.

**#2 — Generated agent files pile up (Option A: reuse if exists)**
- `agent_factory.py` checks `os.path.exists(file_path)` before calling CodingAgent. If the file is already there, generation is skipped entirely.
- Files accumulate once per unique `agent_name`, not once per run.

**#6 — No memory across runs**
- `orchestrator.py` calls `memory_manager.retrieve("last_run_summary")` at the start of each request and injects prior context into the meta-agent prompt.
- After each run, stores the full result under `run:<correlation_id>` and updates `last_run_summary`.

**#7 — Everything synchronous/blocking**
- `orchestrator.py` has a streaming `yield`-based method (lines ~1218–1273) that emits progress events after each agent step.

**Agent status never reaching "completed" (priority table)**
- `agent.complete()` is called in `process_user_request()` after all tasks for an agent finish.

**`open()` false positive in `_DANGEROUS_PATTERNS`**
- The security scanner flags any `open(` call, including legitimate config reads in generated agents.

**#5a — `llm_router` never used in `process_user_request`**

- Fix: pass `llm_router=self.llm_router` when constructing `Meta_agent`.

**#5b — BudgetManager monitors but never gates LLM calls**

#### New issues found

**N1 — `supabase_client.py` uses `print()` instead of logger**
- `supabase_client.py` has 7 `print()` calls (connection OK, insert response, error messages). These go to stdout and can't be filtered, redirected, or suppressed in production.
- Fix: replace all `print()` calls with `logger.info()` / `logger.error()`.

**N2 — `record_token_usage` in BudgetManager uses `hasattr` anti-pattern**
- `budget_manager.record_token_usage()` checks `if not hasattr(self, "token_usage")` to lazily init a list that should be in `__init__`. Same pattern in `record_time_usage` with `self.time_records`. This is fragile — if `__init__` is ever called without these assignments, the attribute exists in some instances and not others.
- Fix: move `self.token_usage = []` and `self.time_records = []` into `BudgetManager.__init__`.

**N3 — `settings.py` and `llm_class.py` use different env var names for the same key**
- `settings.py` defines `GOOGLE_API_KEY` but `llm_class.py` reads `GOOGLE_GEMINI_API_KEY`. Anyone who sets `GOOGLE_API_KEY` (per settings) will find Gemini calls failing silently.
- Fix: standardise — either update `llm_class.py` to read `GOOGLE_API_KEY` or update `settings.py` to match `GOOGLE_GEMINI_API_KEY`.

**N4 — `settings.py` defines `ANTHROPIC_API_KEY` but Claude is not supported in `llm_class.py`**
- The settings file documents Anthropic support, but `LLM.__init__` has no `elif model.startswith("claude")` branch. Attempting to use a Claude model raises `ValueError: Unsupported model`.
- Fix: either add Claude/Anthropic support to `llm_class.py`, or remove `ANTHROPIC_API_KEY` from settings to avoid confusion.

**N5 — No rate limiting on API endpoints (OWASP: API4 — Unrestricted Resource Consumption)**
- The FastAPI routes have no request rate limiting. A single user (or attacker) can hammer `/api/v1/agents/` or POST `/tasks/` in a tight loop, triggering unlimited LLM calls and DB writes.
- Fix: add `slowapi` or a similar rate-limit middleware. Apply stricter per-user limits on the `/agents/run` (or equivalent LLM-triggering) endpoint.

**N6 — Task `status` filter in `list_tasks` is not validated against `VALID_STATUSES`**
- `task_routes.py` defines `VALID_STATUSES` and validates it on PATCH, but `list_tasks` (GET) accepts any `status` query param without validation. An invalid status just returns an empty list silently instead of a 400 error.
- Fix: add `if status and status not in VALID_STATUSES: raise HTTPException(400, ...)` at the top of `list_tasks`.

**N7 — `_active_agents` dict grows without bound in Orchestrator**
- `register_active_agent()` adds to `_active_agents` but nothing removes agents after `process_user_request` completes. After N requests the dict holds N×agents references in memory.
- Fix: call `unregister_agent(agent.agent_id)` for each agent at the end of `process_user_request` (after results are collected), or call the existing `track_active_agents()` cleanup at the end of the request.

**N8 — `LLMRouter` has no registered endpoints at startup**
- `LLMRouter.__init__` starts with `self._endpoints = {}`. Nothing in `initialize_subsystems` or anywhere else calls `llm_router.register_endpoint(...)`. The router is initialised but has no models to route to, so even if wired in, `route_request()` would fail or fall back to nothing.
- Fix: populate the router from config/settings in `initialize_subsystems()` after creating it — register at least the default LLM as an endpoint.

Flaws — most important first
1. The "safe" code sandbox is trivially escapable, and it's wired directly into the coding agent's execute path.
In coding_agent.py:34-37, generate_code has the LLM write code from a free-text spec and immediately auto-executes it via a fresh CodeExecutor().execute(...) — no enable_sandbox() call, so Docker mode never activates.

For Python: code_executor.py:143-219 restricts __builtins__ but still includes getattr, setattr, type, object, vars — classic ingredients for a sandbox escape (().__class__.__bases__[0].__subclasses__()...) since attribute access isn't gated by builtins at all. This is a well-known-broken pattern, not a real sandbox.
For Bash/JS: execute_bash and execute_javascript just shell out via subprocess.run with zero containment unless Docker mode is explicitly enabled — which it isn't by default, and the Docker-detection path is skipped entirely on Windows (os.name == "posix" check).
The regex "dangerous pattern" blocklist (detect_dangerous_patterns/sanitize_code) is never called from execute()/execute_python()/execute_bash() — it exists but isn't actually a gate, and regex blocklists are bypassable anyway.
Net effect: any user hitting the "generate code" task with language: bash gets something close to arbitrary command execution on the host. This is the one to fix before this touches real code/data.

2. ToolExecutor.execute() never calls its own permission/rate-limit checks. tool_executor.py:63-140 validates tool availability and inputs, but check_permissions() and check_rate_limit() (lines 316-346) are fully implemented and never invoked anywhere in the execution path. Same "safety code exists but isn't plugged in" pattern as #1.

3. Path traversal + Zip Slip in file_handler.py.

_resolve() only prepends base_path for relative paths — an absolute path or ../../ traversal bypasses the sandbox root entirely.
decompress() calls zf.extractall() / tf.extractall() with no member-path sanitization — a malicious archive (e.g. an agent downloading/extracting something) can write files anywhere on disk (classic Zip Slip).
The extension allowlist (_check_allowed) is only enforced on read/write/create/append — not on delete, copy, move, decompress.
4. Auth works but is inefficient/inconsistent. auth.py does a live network round-trip to Supabase on every request to verify the JWT, instead of local verification. SUPABASE_JWT_SECRET is defined in .env but appears unused — looks like local verification was intended but never implemented.

Good news: .env is properly gitignored and not in git history, CORS isn't wildcarded with credentials, and the JWT auth middleware itself is reasonably sound.

Bottom line
Building an IDE on top is a sound direction, but before wiring the coding agent up to anything real: fix the code-execution path first (make Docker/gVisor sandboxing mandatory, not opt-in, and delete the illusion of a Python "safe builtins" sandbox), fix the file-handler traversal/zip-slip issues, and wire the existing-but-unused permission/rate-limit checks into ToolExecutor.execute().
